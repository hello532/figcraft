Design system template: foundations first, components second

Foundations at 1440 × 1080, then components. Local styles and variables with modes carry the tokens; component sets and their variants carry the states.

What's in the starter

The project publishes the name of this starter, not its internal pages or frame sizes. What follows is a workable structure for this kind of file — a starting spec to build against — not a transcription of the shipped document. Check it against the build you actually open.

Four pages: foundations, components, modes, and an inventory sheet that lists every component next to its properties. Foundations are the source of truth; components only reference them.

  • Foundations / ColorFour ramps of ten steps each (50 through 900), plus semantic aliases — surface, border, text, accent — that point at the ramps.
  • Foundations / TypeAn eight-step scale at 12, 14, 16, 20, 24, 32, 40 and 56 px with line heights 16, 20, 24, 28, 32, 40, 48 and 64; each row is a text style, not a styled copy.
  • Foundations / SpaceThe 4-based spacing scale and three radii (4, 8, 16 px) shown as measured blocks, so you can see the steps rather than read them.
  • Components / ButtonsThree sizes × four emphases × three states as one component set, with a text property for the label and an instance-swap property for a 16 px icon slot.
  • Components / InputsText field, select, checkbox, radio and toggle, each with default, focus, filled and error states, plus a 72 px label-and-help block.
  • Components / CardsA 320 px card with a media slot, a heading, a two-line body and one action; a boolean property toggles the media slot without detaching.
  • InventoryEvery component set listed with its properties in a table, which is the sheet you send when someone asks what exists.

Canvas spec

Sheets are 1440 × 1080 with 96 px margins, which leaves 1248 px of content — room for ten 96 px color steps with 8 px gaps, and for component rows that will not fit on a laptop screen without scrolling.

Open it

  1. File ▸ New from template — then choose “Design system”. The four pages arrive together, already arranged in the order you should read them.
  2. Save the file — this is the starter you keep for years: name it after the product, and put it in version control if your team does that.
  3. Read the foundations pages before editing components — components reference styles and variables, so changing a token updates every instance.
  4. Decide the two modes early — light and dark are variable modes, not duplicate pages. Adding a third mode later is cheap; retrofitting one after 200 hard-coded fills is not.
  5. Check fonts first — the type sheet is meaningless if text falls back because ../craft-fonts is missing.

Make it yours

The starter is a structure, not a palette. Replace tokens, keep the structure.

Variables

Aliases, not duplicates

Semantic names point at ramp steps. When the ramp changes, the alias follows and every component using it follows too — that is the whole point of the sheet.

Modes

Light and dark, one file

Modes let one component set render two themes. Verify text pairs with the contrast checker, and build your ramp in the palette generator first.

Components

Properties beat copies

Booleans, text properties and instance swaps cover most state needs. A variant for every combination multiplies; a property that toggles one attribute does not.

Styles

Text and effects

Text styles hold the scale; effect styles hold blur, noise and glass recipes so a card does not invent its own shadow. Local styles stay local to the file.

What it does not give you

This is a library in a file, not a published library. FigCraft has no accounts, teams or cloud sync — multiplayer is a preview, and there is no equivalent of a published, versioned library that other files subscribe to. Copy the file, or keep one person responsible for it.

Also be clear about the ceiling: the project's own parity estimate is about 49%, so some token and component behaviours you know from Figma will be missing or shaped differently. Export CSS, HTML or React gives you a snapshot of a frame; your variable names stay in the .figcraft archive rather than travelling into the output, so treat the foundations pages as the documentation. See known issues before you standardise a team on it.

Questions this page answers

Straight answers, with the limits stated. Every claim here is checkable against the sources linked above.

Does the design system starter include a published library?

No. It is a library inside one file. FigCraft has no accounts, teams or cloud storage, and multiplayer is a preview without team permissions. Sharing means sharing the .figcraft archive, and keeping one owner for the file is the practical substitute for publishing.

How many colors and type styles does it ship?

Four color ramps of ten steps, an alias row for semantic names, and an eight-step type scale from 12 to 56 px with matching line heights. The space sheet adds a 4-based spacing scale and three radii. All of it is editable in one place.

Can I add a third theme?

Yes — add a variable mode and give the aliases values for it. Modes are engine features, so the components do not need duplicating. Doing this at the start is far cheaper than retrofitting after the components have hard-coded fills.

Why does exporting CSS not produce my token names?

Export is a snapshot of a frame, not a token build. The CSS, HTML or React output reflects what is drawn, while your variable names live in the .figcraft archive. Keep the foundations pages as the record and write the token layer yourself if you need one.
