Designing offline with FigCraft

FigCraft stores documents as .figcraft archives on your disk, with no account and no telemetry. That is a real trade: total ownership of the file, and total responsibility for it.

Independent guide·Updated 2026-10-22·Covers FigCraft v0.9.0·6 min read
Download FigCraftOpen the studio

The model in one paragraph

A FigCraft document is a .figcraft archive on your filesystem. There is no sign-in, no workspace, no server component in the loop, and no telemetry — nothing leaves the machine unless you share it deliberately. The app is native Rust on macOS, Windows, Linux and FreeBSD, so the same document opens on any of them without a network round trip.

This is the part of the project that is genuinely finished, not a preview: local editing is the primary workflow, not a fallback. Collaboration is the preview.

What stays local, and what leaves

ThingWhere it lives
Document content and historyThe .figcraft file you saved; undo history is in the session
Account, team, workspaceDoes not exist
TelemetryNone
FontsBuilt into the app plus your system fonts; a source build also needs the craft-fonts checkout
A live sessionLeaves only when you host, join or publish one on a collaboration server
Exports you uploadLeave when you upload them; the exporter itself writes to disk or returns bytes

Step by step: an offline setup that survives

  1. Use a native build, not the web build. The WebAssembly build is the editor in a tab; a desktop build is the one that owns files on disk. 
    # macOS
open figcraft-0.9.0-macos-universal.dmg
# Linux, no install step
chmod +x figcraft-0.9.0-linux-x86_64.AppImage && ./figcraft-0.9.0-linux-x86_64.AppImage
  2. Keep one file per product, saved as .figcraft. Import once, then work in the native format. Converting on demand keeps the archive authoritative: 
    # build the CLI once, or use the AppImage's cli subcommand
cargo build --release -p figcraft-cli
./target/release/figcraft-cli convert brand-source.fig brand.figcraft
  3. Put the file under version control. A .figcraft is a binary archive, so history is snapshot-based rather than line-based — but a commit per milestone is still the cheapest undo you will ever get. 
    mkdir -p ~/work/brand && cd ~/work/brand
git init
cp ~/Downloads/brand.figcraft .
git add brand.figcraft
git commit -m "brand: first .figcraft import from v0.9.0"
  4. Keep a second copy off the machine. With no cloud there is no server-side history. A nightly rsync to another disk is the whole backup strategy: 
    rsync -a --delete ~/work/brand/ /Volumes/Backup/brand/
  5. Share deliberately, if at all. The collaboration server is a separate optional binary, and live sessions are a preview with no accounts or teams. Self-host it rather than trusting a public instance: 
    cargo run --release -p figcraft-server
  6. Check the claim yourself. With the app open and a document loaded, watch outbound traffic for a minute. Nothing should be initiating connections: there is no account, so there is nothing to phone home about.

What can go wrong

  • The file is gone and there is no cloud copyThis is the model. A launch crash on macOS 27.0.1 with an M1 machine (#781) is a work-stopping event precisely because nothing is stored elsewhere for you. Keep the off-machine copy before you need it.
  • You assumed the live session encrypted everythingThe optional server is not end-to-end encrypted on a public instance. Self-host it, or do not use it for material you would not post.
  • Your fonts are wrong on the second machineFonts are local. A missing family falls back silently in the document (#752), so the same file can look different on two laptops. Install the families on both.
  • You edited the import and never saved a .figcraftRecovery is a local file, not a server snapshot. Save to the native format before you invest an hour in edits.

Unverified: the absence of telemetry was not packet-inspected for this page; it is the project's stated design and the reason there is no account system. Backup commands shown are generic shell, not FigCraft features.

Questions this page answers

Straight answers, with the limits stated. Every claim here is checkable against the sources linked above.

Does FigCraft work offline?

Yes, by design. Documents are .figcraft archives on your disk, there is no account and no telemetry, and nothing leaves the machine unless you explicitly share it or join a live session.

Where are my files stored?

Wherever you saved them: a .figcraft archive on the local filesystem. There is no server-side copy, so the file you saved is the only copy unless you make another.

Does FigCraft have cloud sync or version history?

No cloud and no accounts. Undo history lives in the session, and the practical substitute for cloud history is putting the .figcraft file in git and keeping an off-machine backup.

Is the collaboration server private?

Only as private as where you run it. figcraft-server is optional and self-hostable; live sessions are a preview with no accounts or teams, and the public server is not end-to-end encrypted.

Can I open the same file on macOS and Linux?

Yes. The native format is the same and builds exist for macOS, Windows, Linux and FreeBSD. Fonts are the caveat: they come from the machine, so install the same families on both.
