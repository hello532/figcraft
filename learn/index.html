Guides

FigCraft guides for the work that actually breaks

FigCraft is an early alpha at roughly 49% parity by the project's own estimate. The useful questions are narrower: will my file open, what does the exporter write, can a script drive this, and what does leaving Figma cost. Eight answers below, each with the commands and the issue that tracks the failure.

The eight topics

My .fig file will not open

Import is best effort: survey the file with the CLI first.

  1. Freeze the original.
    cp brand-source.fig brand-source.fig.keep
shasum -a 256 brand-source.fig.keep   # sha256sum on Linux
  2. Build the CLI.
    cargo build --release -p figcraft-cli
./target/release/figcraft-cli --help
  3. Survey without a window. info prints pages, node counts, frames, styles, variables and missing fonts, sending unimported material to stderr as note: lines.
    ./target/release/figcraft-cli info brand-source.fig --json > import-report.json
  4. Convert a copy, then edit the native file.
    ./target/release/figcraft-cli convert brand-source.fig brand.figcraft
  5. If it stalls, slice by frame — export the worst frames from Figma as SVG and convert each alone.
    ./target/release/figcraft-cli convert home.svg home.figcraft

What goes wrong: a large file fails or takes very long (#574, umbrella #321, with large-file opening improved in #315); grid auto layout arrives without tracks (#465); instance-swap overrides fall back to the main default (#464); and the import does not report all it discarded (#467).

Unverified: how much of any file survives. Coverage is file-dependent; #467 says reports can omit losses.

My SVG looks nothing like the canvas

One Rust exporter serves the app and CLI. The studio at /#demo cannot read .figcraft and renders differently; do not diff the two.

  1. Confirm the target. --node and --page take a name or id.
    ./target/release/figcraft-cli info app.figcraft
  2. One layer, one file.
    ./target/release/figcraft-cli export app.figcraft -o hero.svg --node "Hero"
  3. Every top-level frame. A directory output has no extension to infer; name the format.
    mkdir -p exports
./target/release/figcraft-cli export app.figcraft -o exports/ --format svg
  4. Rasters from the same source. PNG, JPG and WebP come from that engine, and --scale (up to 64) applies to rasters only, so the SVG is unchanged.
    ./target/release/figcraft-cli export app.figcraft -o exports/ --scale 2
  5. Print, or outline text. PDF keeps frames as separate pages; the automation export takes svgOutlineText, and export.add stores it per layer. Inspect generates CSS, HTML, React, Leptos, SwiftUI and Compose for handoff.
    ./target/release/figcraft-cli export app.figcraft -o screens.pdf --page "Screens"

What goes wrong: SVG and PDF export refuse a document with visible descendants more than 256 levels below the exported root, and the old destination stays — check the exit code, not the timestamp; text stays <text> unless outlined, so a viewer lacking the family differs; a missing font is laid out in a fallback first (#752, rescan and refit under #821).

Unverified: byte-level fidelity across viewers. Syntax was checked against the CLI docs, not real output.

The keys from the demo do nothing

The demo's keys, not the app's: V/F/R/T tools, Delete, Cmd/Ctrl+Z (Shift redo), Cmd/Ctrl+D, Cmd/Ctrl+C/V, arrows 1 px (Shift 10, Alt 0.001), Cmd/Ctrl+arrows resize, Space+drag pan, Cmd/Ctrl+wheel zoom, ? dialog.

  1. Print the real table. commands lists label, shortcut and undoable marker.
    ./target/release/figcraft-cli commands --filter export
  2. Make it machine-readable.
    ./target/release/figcraft-cli commands --json > commands.json
  3. Read the platform binding. list_commands over MCP reports each command's first key for the server's platform — run it where you work.
  4. Check an ambiguous key by its command. Use as mask is Ctrl+Cmd+M on macOS, Ctrl+Alt+M elsewhere; your build is authoritative.
  5. Skip the keymap in automation. run_command reaches a command by id; key resolves keys as the canvas does.

What goes wrong: a shortcut types a character while a text layer is edited, because text keys win; and labels may be unreadable — the UI is small on 1440p (#540), addressed by the interface-size preference (#818).

Unverified here: the real app's keymap, not reproduced because it changes between releases and platforms.

There is no cloud copy of my file

A document is a .figcraft archive on disk: no sign-in, no workspace, no server, no telemetry. Local editing is finished; collaboration is a preview.

  1. Use a native build, not the web build. WASM is an editor in a tab; the desktop build owns files.
    chmod +x figcraft-0.10.0-linux-x86_64.AppImage
./figcraft-0.10.0-linux-x86_64.AppImage
  2. Work in the native format.
    ./target/release/figcraft-cli convert brand-source.fig brand.figcraft
  3. Version the file. A .figcraft is binary, so history is snapshot-based — a commit per milestone is cheapest.
    git init
cp ~/Downloads/brand.figcraft .
git add brand.figcraft
  4. Keep a copy off the machine. No cloud means no server-side history.
    rsync -a --delete ~/work/brand/ /Volumes/Backup/brand/
  5. Share deliberately, if at all. Self-host the optional server rather than trust a public one.
    cargo run --release -p figcraft-server

What goes wrong: a launch crash on macOS 27.0.1 with M1 (#781) is work-stopping because nothing is stored elsewhere; a missing family falls back silently, so one file differs across laptops (#752); and the public server is not end-to-end encrypted.

Unverified: telemetry absence was not packet-inspected; it is the project's stated design. Backup commands are generic shell.

I need an agent to drive the app

JSON-RPC 2.0 over stdio, exposing the same 400+ commands as the menus. Headless is an in-process session with one untitled document and no window; attached drives a running app.

  1. Build the CLI and use its absolute path in client configs; relative paths break when the client starts elsewhere.
    cargo build --release -p figcraft-cli
  2. Start it headless for scripted work.
    ./target/release/figcraft-cli mcp
  3. Or attach to a running app. The channel listens on 127.0.0.1 only; --attach takes host:port too.
    figcraft --control 7979
./target/release/figcraft-cli mcp --attach 7979
  4. Register it with Claude Code.
    claude mcp add figcraft -- /absolute/path/to/target/release/figcraft-cli mcp
  5. Confine what it touches. Both flags repeat, folders must exist, and writes outside the roots are refused.
    ./target/release/figcraft-cli mcp --automation-read-root /work/project --automation-write-root /work/project/out

What goes wrong: a line is capped at 32 MiB, and an oversized or unterminated frame returns -32600 and closes the session; root flags cannot combine with --attach, so start the app with them; attached calls are never replayed after a transport failure; open reports include #927 and #967; CI renders need --no-system-fonts.

Unverified: which third-party MCP clients work end-to-end. Read results back with inspect_document or screenshot.

I have to build 300 screens overnight

The same engine without a window: usage errors exit 2, failures exit 1, scripts land whole or not at all.

  1. Inspect first. --json gives a machine-readable report.
    ./target/release/figcraft-cli info app.figcraft --json > report.json
  2. Export deterministically. A directory output gives one file per top-level frame.
    ./target/release/figcraft-cli export app.figcraft -o exports/ --scale 2
  3. Run a command script — a JSON array of command/params pairs, where a later step refers to an earlier result with {"$step": n}.
    ./target/release/figcraft-cli run start.json --out dashboard.figcraft
  4. Confine the run. Both roots repeat; every file touched must fall inside them.
    ./target/release/figcraft-cli render in/doc.figcraft -o out/ok.png --automation-read-root in --automation-write-root out
  5. Print the command table, not a guess.
    ./target/release/figcraft-cli commands --filter layout

What goes wrong: a failing step prints "ok": false and "rolledBack": true, writes nothing including --out, restores the session and exits 1; a path outside the roots is refused, which is confinement working (#839); render fits the page to 16384 px; renders differ between machines without --no-system-fonts.

Unverified: wall-clock timings. Exit codes, the render cap and rollback come from the CLI docs.

The AppImage will not start

Match architecture first — an aarch64 build will not start on x86_64. Files are figcraft-0.10.0-linux-ARCH.FORMAT.

  1. Verify the download.
    sha256sum -c SHA256SUMS.txt --ignore-missing
  2. AppImage: no install step. The file is the application, and bundles the CLI.
    chmod +x figcraft-0.10.0-linux-x86_64.AppImage
./figcraft-0.10.0-linux-x86_64.AppImage cli info app.figcraft
  3. Or let the distro own the binary. x86_64 and aarch64 ship all six formats; riscv64 deb, rpm, tarball only.
    sudo apt install ./figcraft-0.10.0-linux-x86_64.deb
sudo dnf install ./figcraft-0.10.0-linux-x86_64.rpm
sudo pacman -U figcraft-0.10.0-linux-x86_64.pkg.tar.zst
flatpak install ./figcraft-0.10.0-linux-x86_64.flatpak
  4. Tarball, also the FreeBSD path. Check what it unpacks into.
    tar -xzf figcraft-0.10.0-linux-x86_64.tar.gz
  5. Source builds need craft-fonts beside the project, or a missing checkout falls back to another font. The browser build needs trunk and cargo xtask wasm.
    git clone https://github.com/storytold/figcraft
cd figcraft
git clone https://github.com/storytold/craft-fonts ../craft-fonts
cargo run --release -p figcraft

What goes wrong: FreeBSD gets one .tar.gz for x86_64 only, because aarch64 was dropped (first announced in v0.9.0) when it could not build inside the CI job's 5-hour limit; deb, rpm, flatpak and Arch are not documented as bundling the CLI; a tiny interface is a 1440p problem (#540) fixed by the interface-size preference (#818); missing families fall back silently (#752).

Unverified: distro runtime dependencies, and whether pacman -U upgrades cleanly. Filenames and the format matrix are checked against v0.10.0.

I am moving a real team file off Figma

A re-platforming with a known finishing cost, not a switch. Live sessions are a preview with no accounts, teams or cloud; nothing replaces Figma comments, libraries or multiplayer.

  1. Inventory what you use — components, variants, variables, modes, fonts. That is the work breakdown.
  2. Start with the smallest representative file and keep the original plus a checksum.
    cp marketing.fig marketing.fig.keep
shasum -a 256 marketing.fig.keep   # sha256sum on Linux
  3. Read the import before opening it. Missing fonts and repairs surface here, though not every drop.
    ./target/release/figcraft-cli info marketing.fig --json > import.json
  4. Own a native file immediately.
    ./target/release/figcraft-cli convert marketing.fig marketing.figcraft
  5. Rebuild in cost order: variables and modes, then components, then instances, then overrides — installing fonts, or loading them with text.loadFont, first.

What goes wrong: the import never finishes (#574, umbrella #321); instance-swap overrides are gone (#464); grid tracks did not import (#465); type sits pixels off because a font was substituted (#752); and teammates cannot comment or co-edit.

Unverified: how much of a real file survives, and how long a rebuild takes. Both are file-specific; #467 makes the report a floor.

Glossary

Fourteen terms that decide whether an import still works.

Auto layout

A frame that places its children by rules — direction, gap, padding, alignment, sizing — not by coordinates, so imports are placed by the layout.

Component

A reusable master layer whose edits reach its instances; the engine treats it as ordinary commands.

Instance

A copy linked to a component that inherits its properties and can carry overrides — what a swap drops.

Variant

One named state of a component, chosen through properties, not by swapping files.

Variable

A named value — colour, number, string, boolean — that layers bind to, not a literal.

Mode

One value set of a variable collection, such as Light and Dark; the first is default.

Alias

A variable whose value is another variable, which is how a token hierarchy carries a change down.

Design token

A named design decision — colour, spacing, radius, type step — stored once and referenced everywhere.

Constraint

How a free-positioned child moves or resizes when its frame resizes; auto-layout children follow the flow.

Inspect

FigCraft's handoff panel: layout, type, fills and effects with style and variable names, plus CSS, HTML, React, Leptos, SwiftUI or Compose.

MCP

The Model Context Protocol, which lets an agent call FigCraft's 400+ commands instead of a private API.

WASM

WebAssembly, the target that compiles the same Rust engine into a browser tab.

.figcraft

FigCraft's native document: an archive on disk holding the layer tree, styles, variables and images, with no account or telemetry.

.fig

Figma's document format, imported best-effort — import a copy, save a .figcraft, keep the original.

What this page does not cover

The real app's keymap is not documented here — print it from your build with figcraft-cli commands, since it changes between releases and differs by platform. Nothing here applies to a build newer than v0.9.0. There are no performance numbers: timings are file-specific and unmeasured, and how much of a given .fig survives is unanswered because the report can omit drops.

Questions this page answers

Straight answers, with the limits stated. Every claim here is checkable against the sources linked above.

Is FigCraft ready for a production design team?

Not as a replacement for a hosted team tool. It is an early alpha at about 49% parity by the project's own estimate, with no accounts, teams or cloud. It is ready for solo interface work on local files, and for developers who want the same command engine in a script and in a UI.

Which version does this page cover?

v0.10.0, on macOS, Windows, Linux, FreeBSD and the WebAssembly build. Commands come from the project's own CLI, MCP and control-protocol documentation for that release.

Does any of this apply to the browser studio on this site?

Only where a topic says so. The studio at /#demo is an independent canvas, not the FigCraft app: different renderer, different shortcuts, different export set, and it cannot read .figcraft.

Can FigCraft open a Figma .fig file?

Yes, on a best-effort basis. Large files are a known failure mode (#574), grid auto layout loses tracks (#465), instance-swap overrides fall back to the main component (#464), and the import does not report everything it discards (#467). Keep the original .fig.

How do I find the real app's keyboard shortcuts?

Print them from your build: figcraft-cli commands lists every command with its shortcut, and --json with --filter narrows the result. Over MCP, list_commands reports each command's first key for the platform the server runs on.

Where do I report a bug or check whether mine is known?

The tracker at github.com/storytold/figcraft/issues. Each topic above links the issues it can verify, and the curated shortlist is on known issues.
